# Skill Creator スキル（Meta Skill）

> 既存スキルの改善、または新規スキルを作成する際に起動するメタスキル。
> AutoAgent知見（`learnings/insights.md` 2026-04-04）の「eval不要・並列不要で使える部分」の具体実装。
> 手動運用（主観評価・小規模）の当リポジトリに最適化した部分適用版。

## 目的

1. **Blueprinting**: 新規スキル作成時に骨格・段階的開示・バンドルリソースをガイド
2. **Testing**: 既存スキルを3〜5回テスト実行し、失敗パターンを分析
3. **Improvement**: 分析結果に基づいてスキルを改善

## いつ起動するか

以下のいずれかに該当する時、ユーザーまたはメインClaudeがこのスキルを起動する:

- 新しいスキルを `.claude/skills/` に追加したい
- 既存スキルの動作が期待通りでない（エッジケースでの失敗・出力品質低下）
- セッション終了時の振り返りで「スキル改善の兆候」を検知した（`session-handoff.md` の一部として）
- 月次で既存スキル一式を定期レビューする（推奨：月初）

## スキル設計の3原則（Progressive Disclosure）

すべてのスキルは以下の3層で情報を配置する:

```
Tier 1（常時ロード）: メタデータ
  - スキル名・1行説明・起動条件
  - メインClaudeのコンテキストに常駐する最小限の情報

Tier 2（マッチ時ロード）: 手順・制約
  - ステップバイステップの実行手順
  - やってはいけないこと（禁止事項）
  - 判断基準

Tier 3（実行時参照）: 例・ヘルパー・テンプレート
  - Few-shot的な実例
  - 決定論的処理を行うヘルパースクリプト
  - 生成物の骨格テンプレート
```

トークン消費を最小化するため、Tier 3 は別ファイルに退避してリンクで参照することを推奨する。

## Phase 1: Blueprinting（新規作成）

### Step 1-1: スキルの必要性を検証

以下の問いに答えられない場合、スキル化を見送り、メインClaudeの通常推論に任せる:

```
┌─ 同じ手順を3回以上繰り返し実行する予定か？
│    NO → スキル不要（1回限りはメインClaudeに直接指示）
│    YES ↓
├─ 手順に明文化できる「制約」「禁止事項」があるか？
│    NO → Tool Use (§4) で十分な可能性
│    YES ↓
├─ 既存スキル（daily-ai-research / html-editing / session-handoff / x-research）の拡張で対応可能か？
│    YES → 既存スキルを編集
│    NO → 新規スキル作成へ
└─ SkillsMP（skillsmp.com）に類似スキルが存在するか？
     YES → フォークして当リポジトリ向けにカスタマイズ
     NO → ゼロから作成
```

### Step 1-2: SKILL.md の骨格を生成

以下のテンプレートに沿って作成する:

```markdown
# [スキル名]

> 1行説明（いつ起動するか・何を実現するか）

## 目的

- 箇条書きで2〜4項目

## いつ起動するか

- トリガー条件を箇条書き

## 実行手順

### Step 1: [ステップ名]

具体的な手順。コマンド・判断基準・出力先を明示。

### Step 2: ...

## 制約・禁止事項

- やってはいけないこと
- 品質基準

## 出力フォーマット

（成果物がある場合のみ）
```

### Step 1-3: 既存スキルとの整合性チェック

新規スキルが以下のルールに違反していないか確認:

- **言語**: 日本語（`CLAUDE.md` ルール）
- **配置**: `.claude/skills/` 直下に `.md` 1ファイル（サブディレクトリ不要の場合）
- **メタデータ**: 最初の3行に「> 1行説明」「目的」「起動条件」を配置
- **重複**: 既存4スキルと機能が重複していない

## Phase 2: Testing（動作検証）

### Step 2-1: テストケース設計

スキル起動をシミュレートする3〜5個のテストケースを用意する:

| ケース種別 | 内容 | 期待結果 |
|---|---|---|
| 典型ケース | 想定通りのトリガー | 正常実行 |
| エッジケース1 | 入力が最小 | 正常実行 or 明示的エラー |
| エッジケース2 | 入力が過大/複雑 | 正常実行 or 明示的エラー |
| 失敗ケース | トリガー条件に合わない入力 | スキルを起動しない |
| 競合ケース | 他スキルと同時トリガーしうる入力 | 正しく切り分け |

### Step 2-2: トレース記録

各テスト実行で以下を記録する:

```
テストケース: [ケース名]
入力: [実際のプロンプト]
───────────────────────────
実行トレース:
  - Step X: [何をしたか]
  - Step Y: [何を参照したか]
  - Step Z: [何を出力したか]
───────────────────────────
出力: [成果物]
判定: ✅ 成功 / ❌ 失敗
理由: [なぜそう判定したか]
```

トレースは `research/skill-tests/YYYY-MM-DD_[スキル名].md` に保存する（ディレクトリは必要に応じて作成）。

### Step 2-3: 失敗パターン分類

失敗が3件以上出た場合、以下に分類する:

| 分類 | 例 | 対処フェーズ |
|---|---|---|
| **トリガー誤判定** | 起動すべきでない時に起動 / 起動すべき時にしない | Phase 3-A |
| **手順欠落** | 必要なステップがSKILL.mdに記載されていない | Phase 3-B |
| **制約不足** | 明文化されていない禁止事項を犯した | Phase 3-C |
| **出力品質** | 手順は正しいが成果物の質が低い | Phase 3-D |

## Phase 3: Improvement（改善）

### 3-A: トリガー誤判定への対処

- 起動条件の記述を具体化（例: 「リサーチ」→「リサーチ / ニュース / 最新情報 / 動向」）
- 起動しない条件（negative trigger）も明記

### 3-B: 手順欠落への対処

- 失敗トレースから欠落ステップを抽出し、SKILL.mdに追記
- ステップ番号は振り直さず、既存番号に `Step 1.5` 等で挿入することで差分を最小化

### 3-C: 制約不足への対処

- 「禁止事項」セクションに1項目追加
- 理由（なぜ禁止するか）を1行で添える（`CLAUDE.md` ルール: 根拠必須）

### 3-D: 出力品質への対処

- 出力フォーマットを明示
- Few-shot例を「良い例」「悪い例」の対で追加
- ヘルパースクリプトでの決定論的検証を検討

### 改善後の検証

改善版で Phase 2 のテストケースを再実行し、失敗が解消されたことを確認する。
改善によって新たに失敗するケースがないか（回帰）も確認する。

## 制約・禁止事項

- **eval化できる前提を作らない**: 当リポジトリは主観評価・手動運用。AutoAgentのような定量評価ループは適用しない
- **Skill Creator自身をSkill Creatorで改善しない**: メタメタループは収束しない。本スキルの改善は人手で行う
- **既存スキルの大改造は避ける**: 差分ベースの改善に留め、互換性を保つ
- **テストトレースを放置しない**: `research/skill-tests/` に保存後、改善完了時に `memory/decisions.md` に要約を記録

## 出力フォーマット

### 新規作成時

```
📝 新規スキル作成完了: .claude/skills/[スキル名].md
━━━━━━━━━━━━━━━━━━━━━━━━
目的: [1行]
起動条件: [1行]
主要ステップ: [箇条書き3〜5項目]

次のアクション:
  → Phase 2 でテスト実行する？ (yes/no)
```

### 改善時

```
🔧 スキル改善完了: .claude/skills/[スキル名].md
━━━━━━━━━━━━━━━━━━━━━━━━
改善箇所: [分類 A/B/C/D]
変更内容: [1〜3行]
根拠トレース: research/skill-tests/YYYY-MM-DD_[スキル名].md

検証結果: ✅ [N]件中 [M]件成功
```
